## 結論：計画は「見る」ものではなく「レビューする」ものにする

Planモードで計画を出させても、流し読みして承認すれば意味がありません。この記事で作るのは、計画のレビューを型にする仕組みです。実物は3つあります。

1. **計画チェックリスト** — 返ってきた計画を上からなぞる確認表
2. **CLAUDE.md追記文「計画の前に確認すること」** — 計画の出し方そのものを先に縛っておく一文
3. **差し戻し指示プロンプト例集** — 計画が甘いときに、そのまま貼って返す文面

管理職200名への調査（taiziii、2026年11月4日発表）では、AI活用で担当者の作業時間が減ったと答えた人が73.5%いたのに、部門の残業時間が減ったと答えたのは48.2%にとどまりました。「変わらない」が40.6%もいます。作業は速くなったのに、夜は減っていない。理由のひとつは、説明できない変更が、あとで直し直しの夜を生むことです。計画レビューは、その夜を先に消すための仕組みです。

## 前提：Planモードの最小限

Planモードは、Claude Codeの権限モードのひとつです。調べものと計画の提案だけをさせて、変更は人が承認するまでさせません。公式ドキュメントの言い方を借りれば、「research and propose changes without making them」。読む・調べるは自由、書くのは承認のあと、という線引きです。

入り方の要点だけ置いておきます。

- Shift+Tabで権限モードを切り替える。ステータスバーに「⏸ plan mode on」と出れば到着。最近のバージョン（v2.1.283以降）は起動直後がauto modeなので、Planモードまで3回押すことになります
- `/plan` を依頼文の頭に付ければ、その1回だけPlanモードになる
- `claude --permission-mode plan` で起動すれば、最初から計画モードのセッションになる

承認の選択肢は3つで、最初は「Yes, manually approve edits」（承認して、編集は1件ずつ確認する）が無難です。ほかに「Yes, and use auto mode」（計画通りと確信があるとき）、「No, keep planning」（計画を直し続けるとき）があります。承認するとPlanモードを抜けるので、もう一度計画を作りたければShift+Tabで入り直します。

## 実物1：計画チェックリスト

計画が返ってきたら、この表を上からなぞります。コピーして手元に置ける形にしました。

```markdown
# 計画チェックリスト（Planモード用）

## 範囲
- [ ] 触るファイルは、頼んだ仕事の範囲内か
- [ ] 「触らない範囲」が明記されているか
- [ ] 秘密情報・本番環境・外部送信に触れる手順が混ざっていないか

## 中身
- [ ] 変更の順番が書かれていて、途中で止めても壊れない区切りがあるか
- [ ] 計画の内容を、自分の言葉で説明できるか（説明できない変更は承認しない）

## 確認と巻き戻し
- [ ] 終わったあとの確認方法が具体的か（実行するテスト、差分の見方）
- [ ] 巻き戻し方法が書かれているか（Gitの履歴、チェックポイント）

## 大きさ
- [ ] 1回の計画で変える量が大きすぎないか（大きい場合は分割を差し戻す）
```

全部にチェックが付く必要はありません。引っかかった項目が、そのまま差し戻しの材料になります。

## 実物2：CLAUDE.mdに足す「計画の前に確認すること」

チェックリストで毎回引っかかる項目は、計画の出し方そのものを縛れば減ります。第2夜で作ったCLAUDE.mdに、次の追記文をそのまま足してください。

```markdown
# 計画の前に確認すること
大きな変更を頼まれたら、編集の前に計画だけを提示すること。計画には次を含めること。
- 触るファイルの一覧と、それぞれの変更内容
- 触らない範囲（変更しないファイル・フォルダ）
- 終わったあとの確認方法（テストコマンド、差分の確認方法）
- 巻き戻し方法
確認方法と触らない範囲が書かれていない計画では編集に入らず、まず計画を補うこと。
```

これを入れておくと、「確認方法が書いていない計画」は最初から出てこなくなります。チェックリスト側の確認も、範囲と確認方法の2点に絞れて速くなります。

## 実物3：差し戻し指示プロンプト例集

計画が甘いとき、口頭で説明し直すより、型で返すほうが速くて正確です。よくある4つの差し戻しを、貼って使える文面にしました。

**範囲が広すぎるとき**

```
その計画だと config/ まで触ることになっています。config/ は触らない範囲にして、計画を作り直してください。
```

**確認方法が弱いとき**

```
確認方法が「動作確認する」だけでは弱いです。実行するテストコマンドと、期待する結果を具体的に書いて、計画を出し直してください。
```

**一度に変える量が大きいとき**

```
一度に変える量が大きすぎます。まず読み取りと集計だけを直す計画に分割して、第一段階だけを提示してください。
```

**巻き戻しが書いていないとき**

```
問題が起きたときの巻き戻し方法が計画にありません。Gitで戻す手順を追記してから、承認待ちにしてください。
```

## 通しで見る：集計スクリプトの修正を頼む場合

月曜の朝、「月次レポートの集計スクリプト、来週までに直しておいて」と振られたとします。前任者が作った仕組みで、自分は触ったことがない。Planモードで「まず計画だけ作って。ファイルは触らないで」と頼むと、計画はだいたいこう返ってきます（例）。

```
計画：
1. aggregate.py を読み、現在の集計手順を確認する
2. aggregate.py の集計条件を新しい様式に合わせて書き換える
3. config/ の設定ファイルも合わせて更新する
4. 実行して動作確認する
```

チェックリストでなぞると、引っかかるのは2点です。3番は触る範囲が広い（config/ は今回の依頼に入っていない）。4番は確認方法が具体的でない。差し戻しは、例集の1本目と2本目を続けて貼るだけです。

計画が自分の言葉で説明できる形になったら承認します。Ctrl+Gを押せば計画をエディタで直接直すこともできるので、文面で直したほうが早い箇所はそちらで直します。

## 使わないほうがいいときと、つまずきやすいところ

差分を1文で説明できる小さな修正には、計画を挟まないほうが速いです。誤字の修正や変数名の変更がそれにあたります。公式ドキュメントにも、その目安が書いてあります。逆に、触ったことのない仕組みを直すときや、影響範囲が読めないときは、このレビューの型が効きます。

つまずきやすいところも3つ、並べておきます。

- Shift+Tabを1回押しただけでは、Planモードに届かない。auto mode起点だと3回です
- 承認のプロンプトが出ているときにShift+Tabを押すと、承認してしまう。抜けたいときは先にEscを押します
- 計画は、そのセッションのものです。別のセッションに持ち越せないので、大きな仕事は計画を小さく区切って進めます

今夜、振られた仕事がひとつあるなら、計画を受け取ったときにチェックリストの「範囲」だけでもなぞってみてください。書き換える前の5分が、直し直しの夜を減らします。

## 次回予告

第4夜は「見えない残業を数える」です。勤務時間外にClaude Codeを使ったセッションの開始・終了時刻は、記録として残ります。その時刻と残業申告を突き合わせて、申告漏れの候補を洗い出す仕組みを扱います。自分で記録をつける話ではありません。
