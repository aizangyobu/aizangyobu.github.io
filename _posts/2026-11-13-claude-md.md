## 結論：書くのは「概要・約束事・コマンド・禁止事項」の4点だけ

CLAUDE.mdは、Claude Codeへの「毎回の説明」を1回に圧縮するためのファイルです。最初から完璧なものを目指す必要はありません。プロジェクトの概要、守ってほしい約束事、よく使うコマンド、やってはいけない禁止事項。この4点を短く書くだけで、毎回の依頼の手戻りが目に見えて減ります。この記事では、項目ごとの書き方と、そのまま使える雛形を公開します。

## CLAUDE.mdとは何か

CLAUDE.mdは、プロジェクトフォルダに置くMarkdown形式の指示ファイルです。Claude Codeは起動時にこのファイルを自動で読み込み、その内容を前提として作業します。人間でいえば、プロジェクトの引き継ぎメモや、チームの申し送りノートにあたります。

置き場所と読み込まれ方の基本は次の通りです。

- **プロジェクト用**: プロジェクトのルートフォルダに置く `CLAUDE.md`。チームで共有する前提や規約を書く場所です
- **個人用**: ホームディレクトリ配下の `~/.claude/CLAUDE.md`。全プロジェクト共通の、自分の作業スタイルを書く場所です
- **階層読み込み**: 作業フォルダの上位フォルダにあるCLAUDE.mdもあわせて読み込まれます。会社全体の共通ルールを上位に、プロジェクト固有のルールを下位に、という分け方ができます

なお、プロジェクトでClaude Codeを初めて使う場合は、対話の中で `/init` と入力すると、プロジェクトの内容をもとにCLAUDE.mdのたたき台を自動生成してくれます。ゼロから書くのが面倒な場合は、まず生成してから直すのが早道です。

## 項目1：プロジェクト概要

最初に「ここは何の場所か」を3〜5行で書きます。

- 何を作っている／何の業務を扱うフォルダか
- 主な技術や道具（言語、フレームワーク、主要ツール）
- 成果物を置く場所や、よく触るフォルダの構成

Claudeがフォルダの中身を推測する手間が減り、的外れな提案が減ります。コードを読めば分かる細部まで書く必要はありません。「何のための場所か」が伝われば十分です。

## 項目2：約束事（規約・スタイル）

続いて「どう作業してほしいか」。業務で効くのはこの項目です。

- 回答や成果物の言語（例：ドキュメントは日本語で書く）
- 命名規則、整形ツールなど、既存のやり方に合わせる決まり
- コメントや文書の文体（例：報告書は常体、顧客向けは敬体）
- 既存ファイルのスタイルを優先し、勝手な流儀変更をしないこと

ポイントは、抽象的な希望ではなく、判断できる形で書くこと。「きれいに書いて」ではなく「整形は既存の設定ファイルに従う」のように、Claudeが従えるかどうかを自分で判定できる書き方にします。

## 項目3：よく使うコマンド

実行、テスト、ビルド、整形など、繰り返し使うコマンドをそのまま書きます。

- 開発環境の起動コマンド
- テストの実行コマンド
- 整形・チェックのコマンド

毎回「テストはどうやって回すんだっけ」とClaudeが探し回る無駄が消えます。人間の新メンバー向け手順書に書くような内容が、そのまま使えます。

## 項目4：禁止事項と確認ルール

安全のための線引きも書きます。活用術と安全はセット、がこの部の方針です。

- 秘密情報（認証情報が入ったファイル等）を読んだり、出力に含めたりしない
- ファイルの削除や上書きは、事前に内容を提示して確認を取る
- 本番環境に関わる操作、外部への送信・公開を伴う操作は、必ず人が確認する
- 判断に迷う場合は、推測で進めず質問する

CLAUDE.mdはあくまで指示であり、権限そのものを制御する仕組みではありません。強い制約が必要な操作については、権限設定の側でも線を引くのが確実です（権限設定の初期値の分け方は、第4夜「許可・確認・禁止の分け方」で扱います）。

## そのまま使える雛形（基本形）

以下が基本形の雛形です。これをプロジェクトのルートに `CLAUDE.md` として保存し、カッコ内を自分のプロジェクトに合わせて書き換えるだけで使い始められます。解説コメント付きの完全版は「部室の道具箱」で配布しています。

```markdown
# プロジェクト概要
- 名称：（プロジェクト名）
- 目的：（何を作る／何の業務を扱うフォルダか）
- 主な技術・道具：（言語、フレームワーク、主要ツール）
- 成果物の置き場所：（フォルダ構成の要点）

# 約束事
- ドキュメントと回答は日本語で書く
- 既存ファイルの書き方・命名・整形ルールに合わせる。勝手な流儀変更をしない
- 変更は小さく分け、1回の作業範囲を明確にする

# よく使うコマンド
- 起動：（例：npm run dev）
- テスト：（例：npm test）
- 整形・チェック：（例：npm run lint）

# 禁止事項
- 秘密情報（.env、認証情報ファイル）を読み書きしない。出力にも含めない
- 本番環境への操作はしない
- 新しい依存関係やツールを勝手に追加しない

# 確認ルール
- ファイルの削除・上書きの前に、対象と理由を提示して許可を取る
- 外部への送信・公開を伴う操作は、必ず事前確認する
- 判断に迷う場合は、推測で進めず質問する
```

## 書かないほうがいいもの

逆に、入れないほうがいいものもあります。

- **秘密情報そのもの** — パスワードやAPIキーをCLAUDE.mdに書くのは厳禁です。「秘密情報に触れるな」という指示と、秘密情報そのものは別物です
- **長大な資料の全文** — 参照してほしい資料は、ファイル名や場所を示すだけに留めます。全文を貼ると毎回の読み込みが重くなり、大事な指示が埋もれます
- コードを読めば分かることの羅列も不要です。フォルダ構成の全ファイル解説などは入れず、推測できない情報に絞ります
- **その場限りの指示** — 一度だけの作業条件は、そのときの依頼文に書くものです。ずっと残るルールだけをCLAUDE.mdに置きます

## CLAUDE.mdは「育てるファイル」

最初は雛形のままで構いません。使っていて「この説明、毎回しているな」と気づいたら、その一文をCLAUDE.mdに足す。逆に「この指示、いつも無視されるな」と感じたら、表現を具体的に直すか、思い切って消す。この往復で、ファイルは自分の業務の型になっていきます。

目安として、最初は数十行で十分です。長さよりも「具体的で、矛盾がなく、守れる量であること」が効きます。
